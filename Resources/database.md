# CA NEXUS DATABASE — COMPLETE AUDIT

## 1. Executive Summary

The CA Nexus database audit reveals a **partially configured but non-functional database layer**. PostgreSQL is running locally via Homebrew and the database/user exist, but **no application tables have been created**. The Alembic migration system is configured but the autogenerated migration fails due to foreign key dependency ordering issues. SQLAlchemy connectivity works at the engine/session level, but the database schema is empty except for the `alembic_version` table. Multi-tenancy is implemented at the application layer via ContextVar middleware, but PostgreSQL Row Level Security (RLS) is not implemented. The database is **NOT READY** for production or continued development until migrations are fixed and applied.

## 29. Database Problems & Root Causes

### Problem 1: Zero Application Tables in Database
- **Evidence**: `psql \dt` shows only `alembic_version`
- **Root Cause**: Alembic autogenerate produced migration with incorrect table creation order (alphabetical vs dependency order)
- **Impact**: Application cannot store or retrieve any data; all endpoints fail
- **Recommended Fix**: Manually create a properly ordered migration, or use `Base.metadata.create_all()` for initial setup, then use migrations for changes

### Problem 2: Alembic Migration Fails on Upgrade
- **Evidence**: `alembic upgrade head` fails with `UndefinedTableError: relation "clients" does not exist`
- **Root Cause**: Autogenerate creates tables alphabetically; `communications` (first alphabetically) has FKs to `clients`, `matters`, `tasks` (later alphabetically)
- **Impact**: Cannot use migration system; schema cannot be versioned
- **Recommended Fix**: Delete autogenerated migration, create manual migration with proper dependency order (firms → users/teams → clients → matters/tasks → dependent tables), or split into multiple migrations

### Problem 3: No Database-Enforced Multi-Tenant Isolation
- **Evidence**: No RLS policies; all filtering in application code
- **Root Cause**: RLS not implemented in models or migrations
- **Impact**: Single bug in query filter exposes cross-tenant data; no defense-in-depth
- **Recommended Fix**: Implement PostgreSQL RLS with `tenant_id` policies using `SET LOCAL app.current_tenant = '...'` in middleware

### Problem 4: No Transactional Outbox
- **Evidence**: No outbox table/model exists
- **Root Cause**: Not designed/implemented
- **Impact**: Event publishing not transactionally safe; potential for lost events or dual-write inconsistency
- **Recommended Fix**: Add `outbox` table with `event_type`, `payload`, `processed_at`, `tenant_id`; publish from transaction

### Problem 5: Credentials in Repository
- **Evidence**: `.env` file contains real password `ca_nexus_dev_password`
- **Root Cause**: `.env` not in `.gitignore`
- **Impact**: Credentials exposed in git history
- **Recommended Fix**: Add `.env` to `.gitignore`; rotate password; use `.env.example` for template

### Problem 6: Weak Development Secret Key
- **Evidence**: `SECRET_KEY=dev-secret-key-for-local-development-only-min-32-chars`
- **Root Cause**: Placeholder secret not rotated
- **Impact**: JWT tokens can be forged in development; bad habit for production
- **Recommended Fix**: Generate strong random secret for development

### Problem 7: Sensitive PII Stored Plaintext
- **Evidence**: Models have `pan`, `aadhaar`, `passport`, `gstin` as plaintext strings
- **Root Cause**: No encryption-at-rest or column-level encryption
- **Impact**: PII exposure if database compromised
- **Recommended Fix**: Implement column-level encryption (pgcrypto) or application-layer encryption for sensitive fields

### Problem 8: No Database Health/Readiness Probe
- **Evidence**: `/ready` endpoint doesn't test database connectivity
- **Root Cause**: Health check not implemented
- **Impact**: Kubernetes/load balancer cannot detect unhealthy DB connections
- **Recommended Fix**: Implement `/ready` to test `SELECT 1` via database session
